## 1. 结论摘要

本报告基于 `project_sale_new` 项目的知识图谱事实，使用最新的 `ontology_v2` 路线生成：


## 5. LLM 精炼明细

### 5.1 场外衍生品名义本金与保证金

规则候选：`本金/保证金`

LLM 建议：

| 项 | 内容 |
| --- | --- |
| 建议概念名 | 场外衍生品名义本金与保证金 |
| 类型 | `business_measure` |
| 置信度 | high |
| 关键字段 | `init_nom_prin`、`dyna_nom_prin`、`absl_nom_prin`、`marg_prop`、`intr_marg`、`init_marg_prop`、`init_marg_bal`、`base_marg_rate` |

业务解释：

该概念记录场外衍生品合约的名义本金和保证金相关指标。名义本金包括初始、动态、绝对等口径；保证金包括保证金比例、余额、初始保证金等口径。它们共同服务于销售管理、风险控制和日报统计。

证据边界：

- 强证据主要来自 `pdata_n.t98_otc_deri_comp_sale_info` 系列表。
- 规则层将名义本金和保证金聚到同一概念，是因为它们在同一业务流程中流转。
- 但从业务语义看，“名义本金”度量交易规模，“保证金”度量风险覆盖，两者不应直接混成一个正式概念。

建议：

- 拆成两个候选概念：
  - 场外衍生品名义本金。
  - 场外衍生品保证金。
- 业务复核时需要确认初始名义本金、动态名义本金、绝对名义本金之间的差异。

### 5.2 合约生命周期关键日期

规则候选：`时间/生命周期`

LLM 建议：

| 项 | 内容 |
| --- | --- |
| 建议概念名 | 合约生命周期关键日期 |
| 类型 | `lifecycle_attribute` |
| 置信度 | medium |
| 关键字段 | `strt_pric_date`、`end_pric_date`、`early_term_date`、`earn_pymt_date`、`term_days`、`payment_date`、`trade_date`、`start_date`、`end_date`、`time_to_maturity` |

业务解释：

该概念描述 OTC 衍生品合约在销售、参考数据、事件日志等上下文中的关键时间点和期限，包括定价起止日、提前终止日、兑付日、期权费支付日、期限天数等。

证据边界：

- 强证据主要来自 `t98` 销售信息表日期字段组。
- 弱证据多来自上游合约要素表，部分字段可能只是源头存储，不一定实际参与下游流转。
- 该概念里可能混入系统日期，如 ETL 日期、更新时间等，正式建模时要剔除。

建议：

- 第一版可保留为“合约生命周期关键日期”。
- 后续可拆分为：
  - 合约约定日期。
  - 实际执行日期。
  - 支付/结算事件日期。
  - 系统处理日期，通常不应纳入业务 ontology。

## 7. 需要业务确认的问题

优先确认：

| 问题 | 影响 |
| --- | --- |
| `agt_id` 是否是 OTC 衍生品销售协议的唯一业务标识？ | 决定“协议”是否可以作为核心实体 |
| `t98_otc_deri_comp_sale_info_tit110/111/112/293` 是不同产品线、快照、分区还是不同实体？ | 决定多个字段组是否应合并 |

| 名义本金和保证金是否应分开治理？ | 决定度量概念拆分 |
| 费率、费用、收益率是否应按指标性质拆开？ | 决定度量体系设计 |
| 期权和 TRS 是否共用同一套费用/收益率 ontology？ | 决定产品线维度 |
| 哪些日期属于业务生命周期日期，哪些只是系统处理日期？ | 防止系统字段进入业务 ontology |
| 人员、机构、客户经理、经办人、引入人是否应拆成角色模型？ | 决定“人员/机构/归属”是否细化 |

## 8. 质量判断

本项目的 ontology 发现质量可以分三层看：

| 层级 | 结论 |
| --- | --- |
| 表主题层 | 质量较好，结果表、源同步表、主数据表、配置表能够区分 |
| 字段组层 | 可用，核心业务对象和度量字段组能被发现 |
| 跨表概念层 | 有价值但需筛选，高分候选较好，低分关系噪声较多 |
| LLM 精炼层 | 增益明显，适合生成业务命名、拆并建议和复核问题 |

当前不建议把所有自动发现结果直接升级为正式 ontology。更稳妥的流程是：

```text
规则发现候选 -> LLM 精炼 -> 业务专家确认 -> 正式纳入 ontology / 语义层
```

## 9. 为什么采用第二版路线

本报告基于 `ontology_v2/` 和 DeepSeek LLM 精炼，更适合回答：

- 这个项目反向发现了哪些业务对象？
- 哪些字段组能形成候选业务概念？
- 哪些概念应该拆分或合并？
- 哪些证据强，哪些只是弱相关？
- 应该让业务专家优先确认哪些问题？

第二版路线的核心优势是：先把字段放回表和血缘上下文中理解，再判断它们是否构成稳定概念。对于 `project_sale_new` 这类没有指标节点、但有较完整表字段和血缘事实的项目，这种方式比单字段相似更可靠。

1. 人工确认 5 个 LLM 精炼概念，尤其是“名义本金 vs 保证金”“交易对手 vs 客户”“费率 vs 费用 vs 收益率”。
2. 对 `人员/机构/归属` 做第二轮细拆，因为当前成员多、范围粗。
3. 对 `产品/标的`、`销售收入/创收` 继续跑 LLM 精炼。
4. 将人工确认后的概念写回为正式 ontology 节点，而不是停留在 `needs_review` 候选层。
5. 后续可以把查询层支持扩展到 ontology 候选和 LLM 精炼结果，用于问答机器人解释项目业务结构。
