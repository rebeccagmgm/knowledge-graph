# t0 项目新版 Ontology v2 发现详细报告

## 1. 报告结论

本报告基于 `t0` 项目的新版 `ontology_v2` 发现结果生成。

项目目录：

```text
/Applications/personal-work/kg_probe/tmp_ontology_practice/tmp_reparse_20260720/new_project_2_latest
```

说明：该项目在历史采集产物中仍叫 `new_project`，但我们对外讨论和项目注册时命名为 `t0`。

本次使用新版 ontology 发现链路：

```text
表主题识别 -> 字段组语义归纳 -> 血缘证据验证 -> 跨表概念对齐 -> DeepSeek LLM 精炼
```

本次已整合 DeepSeek 对高价值 ontology 候选的二次精炼结果。LLM 的作用不是替代规则发现，而是基于候选概念、代表表字段、血缘证据和跨表关系，对概念命名、类型、边界、拆分建议和待确认问题做语义校准。

总体判断：

- `t0` 不是一个狭义的 T0 交易项目，而是一个覆盖多类经营、客户、产品、组织、收入、两融和交易表现的指标资产集合。
- 新版 `ontology_v2` 适合理解这个项目的业务结构，因为它能从表和字段组层面还原项目包含哪些业务对象、业务度量和数据资产主题。
- 本项目的候选主题明显集中在：
  - T0 交易表现。
  - 客户、交易对手和客户基础信息。
  - 产品、份额、产品销售关系。
  - 员工、机构、组织层级和开发关系。
  - 创收、收入切分、佣金、费用和费率。
  - 净资产、AUM、产品保有。
  - 两融、保证金、息差、股票质押。
  - 场外 / OTC / 期权 / TRS 相关资产。
- 新版发现能形成一张“候选业务 ontology 草图”，DeepSeek 精炼进一步暴露出哪些规则候选是成立的、哪些需要拆分、哪些被规则误归类。最终正式 ontology 仍需要业务专家确认。

## 8. DeepSeek LLM 精炼结果

### 8.1 精炼明细

| 规则候选 | LLM 建议概念名 | 类型 | 置信度 | 关键判断 |
| --- | --- | --- | --- | --- |
| 交易对手/客户 | 交易对手/客户 | `business_object` | 高 | `pty_id`、名称、状态、分类、评级、地址等字段共同指向交易对手/客户主对象，但后续应拆成基础信息、状态、分类、评级、地址等子概念。 |
| 交易对手/客户 | 交易对手/客户标识 | `business_object` | 高 | 资本交割流水中的 `client_id`、`client_group` 是局部客户标识概念，不宜直接等同于完整客户主数据。 |
| 人员/机构/归属 | 机构归属 | `business_attribute` | 高 | `branch_no`、`op_branch_no` 更像交易或操作发生时的机构归属属性，而不是完整机构实体。 |
| 交易对手/客户 | 客户类型 | `reference_data` | 中 | 产品费率表中的 `cust_type`、`cust_type_name` 是客户分类参考数据，不是完整客户对象。 |
| 合约/协议 | 衍生品合约销售信息 | `business_object` | 高 | `t98_otc_deri_comp_sale_info_*` 多张变体表共同描述 OTC 衍生品合约销售信息。 |
| 合约/协议 | 证券持有协议 | `business_object` | 高 | `agt_id`、`agt_modifr`、`ast_acct_agt_id` 等字段稳定指向证券持有协议。 |
| 交易对手/客户 | 客户 | `business_object` | 高 | 互联网增值服务相关表中沉淀了客户、机构、部门等客户维度信息。 |
| 合约/协议 | 限售股卖出控制信息 | `business_object` | 高 | 规则把它归入合约/协议，但 LLM 判断核心语义应是限售股卖出控制。 |
| 交易对手/客户 | 交易对手/客户基础信息 | `business_object` | 高 | 交易交割事件系列表中的客户字段更像事件快照中的客户基础信息。 |
| 合约/协议 | 合约/协议 | `business_object` | 中 | 该类覆盖融资融券、回购、信用、金融行权等多种协议，正式 ontology 应继续按协议子类型拆分。 |
| 合约/协议 | 经纪客户 | `business_object` | 中 | 规则候选名偏差较大，LLM 判断相关表核心是经纪客户，而不是合约本身。 |
| 交易对手/客户 | 客户 | `business_object` | 高 | 经纪客户主数据表中存在客户名称、编号、类型、分类、状态等稳定客户概念。 |
| 交易对手/客户 | 客户查询事件客户信息 | `business_object` | 高 | 客户查询事件表里的客户字段应理解为事件中的客户信息，而不是客户主数据本体。 |
| 合约/协议 | 资产账户代理协议 | `business_object` | 中 | `ast_acct_agt_id`、`ast_acct_agt_modifr` 跨 T0、算法交易、账户策略场景复用，适合单独建概念。 |
| 合约/协议 | 协议/合约 | `business_object` | 高 | 事件表中有资产账户、证券账户、基金账户、收费、期权组合等多类协议标识，应继续拆成协议类型族。 |

### 8.2 LLM 精炼带来的新增认识

本次 DeepSeek 精炼最有价值的地方不是多生成了 15 个名字，而是帮我们把规则发现的候选概念做了三类校准：

1. **纠正规则粗分类**
   - 规则中的 `合约/协议` 是一个很宽的桶。
   - LLM 识别出其中有些其实是 `经纪客户`、`限售股卖出控制信息`、`资产账户代理协议`，说明规则命中字段相似性后，还需要语义层再判断“这个字段组到底在服务哪个业务对象”。

2. **区分对象、属性和参考数据**
   - `交易对手/客户` 里既有完整客户对象，也有客户标识、客户类型、事件中的客户快照。
   - LLM 把 `客户类型` 标为 `reference_data`，把 `机构归属` 标为 `business_attribute`，这对正式 ontology 很关键，因为它避免把所有字段族都建成实体。

3. **暴露拆分边界**
   - 客户类建议拆为基础信息、状态、分类、评级、地址、事件快照。
   - 协议类建议拆为融资融券合约、证券持有协议、资产账户代理协议、收费协议、期权组合协议等。
   - 这说明当前 ontology 不是一次性生成“标准答案”，而是生成可复核、可拆分、可治理的候选结构。

### 8.3 对 t0 项目的业务理解补充

LLM 精炼结果说明，`t0` 项目的底层业务骨架至少包含两条很强的主线：

| 主线 | 说明 |
| --- | --- |
| 客户 / 交易对手主线 | 覆盖客户主数据、客户分类、客户状态、客户评级、客户机构归属、客户事件快照。 |
| 协议 / 账户 / 合约主线 | 覆盖证券持有协议、资产账户代理协议、融资融券和回购等协议族，以及部分限售股卖出控制类业务对象。 |

结合前面的表主题画像，还可以看到另外几条尚未充分进入 LLM 精炼的主线：

- T0 交易表现。
- 创收与收入切分。
- 产品与标的。
- 员工、机构、销售和服务关系。
- 两融、保证金和息差。

也就是说，本次 LLM 精炼已经证明方法有效，但 15 个候选还不能覆盖 `t0` 的全部业务域。下一步如果要把 t0 ontology 做厚，应把 LLM 精炼从“跨表概念候选”扩展到“主题域 + 表组 + 字段组”的组合摘要。

## 11. 当前局限

### 11.1 LLM 精炼覆盖范围有限

本次已经完成 15 个高价值候选概念的 DeepSeek 精炼，但覆盖范围仍然有限。因此：

- 已精炼部分主要集中在客户、交易对手、机构归属、合约协议等候选。
- T0 交易表现、创收与收入切分、产品与标的、两融息差等主题仍主要来自规则和表画像。
- 当前 LLM 精炼对象是“跨表概念候选”，还没有覆盖所有表组、字段组和主题域。

### 11.2 项目过大，弱关系较多

跨表候选关系达到 12,000 条，其中低置信关系为 11,166 条。原因是：

- 项目覆盖业务域太多。
- 客户、员工、机构、产品等通用字段在很多表中重复出现。
- 字段组级对齐仍会受到通用字段名影响。

因此不能把所有关系都作为确定知识，只能作为候选。

### 11.3 通用概念需要拆细

当前规则概念粒度较粗：

| 当前概念 | 建议拆分 |
| --- | --- |
| 交易对手/客户 | 客户、交易对手、当事人、联系人、清算方 |
| 人员/机构/归属 | 员工、机构、营业部、分公司、开发关系、服务关系、销售关系 |
| 合约/协议 | 账户协议、融资融券合约、OTC 合约、产品销售认领关系、事件编号 |
| 时间/生命周期 | 业务日期、交易日期、开户/销户日期、合同日期、系统 ETL 日期 |
| 费率/费用/收益率 | 佣金、费用、税费、费率、收益率、折算率 |

## 12. 建议下一步

建议分三步推进：

1. **先人工确认一级 ontology 草图**
   - 客户、产品、员工机构、收入、资产、两融、T0 交易、规则配置。
   - 这一步不追求字段级完整，只确认一级业务对象是否成立。

2. **继续扩大 LLM 精炼覆盖**
   - T0 交易表现。
   - 创收和收入切分。
   - 客户产品销售关系。
   - 员工机构归属。
   - 两融/保证金/息差。

3. **将确认后的概念写回正式 ontology 层**
   - 自动候选保持 `needs_review`。
   - 人工确认后升级为正式概念。
   - 查询层优先使用正式概念，候选概念只作为探索上下文。

## 13. 本次报告结论

新版 `ontology_v2` 对 `t0` 的效果是成立的，而且比旧版更适合理解项目。DeepSeek 精炼进一步证明：规则可以负责召回候选结构，LLM 更适合负责概念命名、边界校准、类型判断和拆分建议。

最重要的变化是：

- 新版看到了“这个项目到底由哪些业务对象、关系、事实表和规则表组成”。
- LLM 精炼看到了“哪些候选概念应当合并、拆分、降级为属性或参考数据”。

对于 `t0`，新版发现最有价值的结果不是 60 个跨表候选概念本身，而是它把项目压缩成了几条可讨论的业务主线：

```text
客户 / 产品 / 员工机构 / 销售关系 / 创收收入 / 资产净值 / 两融保证金 / T0交易表现
```

这已经可以作为后续构建正式业务 ontology 的输入。更准确地说，它不是直接产出正式 ontology，而是把海量字段、表和血缘压缩成业务专家可以复核的候选概念、候选边界和候选治理问题。
